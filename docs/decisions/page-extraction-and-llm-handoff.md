# 페이지 추출과 LLM 전달 방식

## Decisions

- 웹 페이지 본문을 Markdown으로 바꾸는 일은 `defuddle` 라이브러리(Node용 `defuddle/node`)를 우리 서버에서 실행해 처리합니다. defuddle 호스팅 API(`defuddle.md/<url>`)는 쓰지 않습니다.
- 대상 페이지는 브라우저가 아니라 서버가 가져옵니다. 브라우저에서 임의 사이트를 직접 fetch하면 CORS로 막힙니다.
- ChatGPT·Claude로 보낼 때는 프롬프트와 본문을 합친 텍스트가 URL에 담길 만큼 짧으면 `?q=` 쿼리로 바로 채워 열고, 길면 합친 텍스트를 클립보드에 복사한 뒤 빈 새 채팅을 열고 붙여넣기를 안내합니다. 항상 전체 본문이 전달되어야 합니다.
- 사용자가 입력한 URL을 서버가 가져오므로 http·https만 허용하고, 내부망·loopback·link-local 주소는 거절하며, 응답 시간(10초)과 크기(5MB)에 상한을 둡니다.
- 쿼리 방식과 클립보드 대체를 가르는 기준은 완성된 URL 길이 8,000자입니다. 두 사이트의 실제 한계를 확인하기 전까지는 추정치입니다.
- 변환 결과는 서버에 저장하지 않습니다. 로그인, 사용자 계정, 변환 기록을 두지 않습니다.

## Boundaries

- 로그인이 필요한 페이지, 자바스크립트로 본문을 그리는 페이지의 완전한 추출은 이 결정이 보장하지 않습니다.
- 자바스크립트 렌더링 페이지를 위한 헤드리스 브라우저는 비용이 커서 도입하지 않습니다.
- LLM API를 직접 호출하는 결정이 아닙니다. 요약·번역은 사용자가 연 외부 채팅이 수행합니다.

## Why

호스팅 API는 요청 수 제한과 유료 요청 블록이 있고 사용자 요청이 제3자 서비스에 의존하게 됩니다. 라이브러리를 직접 쓰면 비용과 한도가 없습니다. 2026-11 시점에 `defuddle` 0.19.6 + `linkedom`을 Node 26에서 실행해 `stephango.com/saw`에서 제목·저자·Markdown 본문이 추출되는 것을 확인했습니다(`example.com`은 저자 없음, 본문만).

채팅 사이트의 `?q=` 방식은 URL 길이 한계가 있어 긴 글을 보내지 못합니다. 그래서 길 때만 클립보드로 대체해 본문 손실을 막습니다.

## Reconsider when

- ChatGPT나 Claude가 본문 전달 방식(쿼리, 파일 업로드 링크 등)을 바꾸거나 긴 입력을 URL로 받게 될 때
- 자바스크립트 렌더링 페이지의 추출 실패가 실사용에서 반복될 때

## Still-rejected alternatives

- defuddle 호스팅 API 호출 — 요청 한도와 비용, 외부 의존이 생깁니다. 자체 서버 부담이 커지면 재검토합니다.
- 항상 클립보드만 사용 — 짧은 글에서도 붙여넣기 단계가 늘어납니다.
